# 产品验收矩阵

> 状态：骨架；随每次改动本文件的提交进入 `main` 后即生效，不单独维护「最后整理」日期戳——各章节内嵌日期与 git 历史即为改动时点的权威记录。
> 出处：lingxi [docs/技术设计/验收矩阵.md](https://github.com/Moshuiwang/lingxi/blob/caa845d77fbd2d6381de304dc6047498aa84c782/docs/技术设计/验收矩阵.md)（142 次修订）；体量预算与分册裁定 [#335](https://github.com/Moshuiwang/lingxi/issues/335)、[#479](https://github.com/Moshuiwang/lingxi/issues/479)，状态对账规则 [#100](https://github.com/Moshuiwang/lingxi/issues/100)；验证：全仓（门禁经约 250 个 PR）；分档 G2（空矩阵骨架 + 一条示例断言 + 覆盖清单示例行，分册机制保留）。
>
> 本文只保存产品与部署的 `V-*` 可验证断言、认领状态和产品合同章节映射。证据层级、关口、CI 与受控环境规则看[验证与门禁](验证与门禁.md)；规划者按[长期执行方法入口](../协作/执行方法.md)所指的方法生成或修订具体 `[tracking]` Execution Trace，实际角色、时点、冻结与修复只看获批 Trace；缺项时退回规划者修订，编排者不得从模板补合同。

实现 Story 只读取并认领与自身范围相关的断言，不需要把整份矩阵加载进每个普通任务。新增或修改产品规则时，必须同步更新对应断言与会变红的检查。

> **分册结构**：本文件是矩阵的**总册**。断言少时全部住在本文第一章；超过下文体量触发线后按产品域切成同目录 `验收矩阵-<产品域>.md` 分册，总册只保留分册索引、体量预算、状态口径与第二章合同条款覆盖清单。总册与全部分册合起来才是完整矩阵；门禁 `scripts/ci/check_acceptance_matrix.py` 与 `scripts/ci/check_matrix_row_size_ratchet.py` 按同一集合读取——分册用**目录扫描**发现而不是写死清单，磁盘上有、总册索引里没有链接的分册判红。

## 体量预算

- **单行棘轮**：`V-*` 断言表格行超过 800B 登记进 `scripts/ci/matrix_row_size_baseline.txt`，只许缩不许涨；未超的不得新超（`scripts/ci/check_matrix_row_size_ratchet.py`）。分册不改变这条：门禁按断言编号在「总册 + 全部分册」这一个集合里丈量。超限时把裁定沿革 / 形成经过移到决策记录或参考证据，cell 内只留判定要点 + 链接。
- **总量触发线**：400KB 或 1500 行，先触发者生效；触线只提示、不卡红。计量单位是每个 `docs/技术设计/验收矩阵*.md` 文件各自独立；某一册触线即提示「下一次改动该分册前先把它再拆一层」，同时打印全部分册合计供人判断整体膨胀。
- **分册预案**：触线后优先「按产品域拆分册」（纯结构重组，断言内容与状态零变化）；另一档「按存活状态归档到 `docs/参考证据/`」也可用。单册再次触线时在该册内部按章节继续拆，不把断言搬回总册。

## 状态口径

状态三态 `未认领 / 已认领 / 已验证`，**只写在断言表的「状态」列**，由 `scripts/ci/check_acceptance_matrix.py` 强制；不在散文里另建进度副本。

| 状态 | 含义 |
|---|---|
| 未认领 | 尚无 Story 负责，不作为当前 Story 合并门槛 |
| 已认领 | 已有 Story 负责，合并前必须有相称测试和证据 |
| 已验证 | 已在声明层级实际通过 |

**对账规则**（保守）：仅当「测试存在 + 语义匹配 + 可指认提交 / PR」三者齐备才改为「已验证」，证据索引以「测试文件::类名 / 方法名 + commit 简写」紧跟在相关表格后的对账说明段落里给出；任何一项存疑（尤其是声明层级含 L4a / L3 但本次未补验、或需要跑真实链路才能证明）一律保持「已认领」不翻转、不补验。「Issue 已关闭」「CI 绿过」不单独当证据。

## 一、关键机制验收矩阵

**每条给出可验证断言，而不是“测试 XX 功能”**——断言必须能判定真假。编号格式 `V-<产品域>-<两位序号>`，全矩阵唯一；编号用于[合同条款覆盖清单](#二合同条款覆盖清单)的逐条核对。层级列写该断言的目标 / 已达证据层级（如 `L2（真库）`、`L2 + L4a`，口径见[验证与门禁](验证与门禁.md#三证据层级)）。

分册索引：暂无分册（触线后建 `验收矩阵-<产品域>.md` 并在此登记链接与断言族）。

### 示例

| # | 可验证断言 | 层级 | 状态 |
|---|---|---|---|
| V-示例-01 | 给定……当……则……（把它换成你的第一条可判定断言） | L2 | 未认领 |

## 二、合同条款覆盖清单

维护机器可读映射：`产品合同条款 → 验收断言编号 → 测试用例`。目标形态是三条检查：每条已认领断言至少一个测试用例、没有引用不存在的断言编号、已验证断言确实在声明层级执行过——**当前门禁只执行**下面[清单本体与门禁实际检查的三条](#清单本体与门禁实际检查的三条)所列内容。

**未认领条款不参与强制**，避免绝大多数条款尚无断言时让门禁直接全红；随切片推进，未认领项逐步归零。

#### 清单本体与门禁实际检查的三条

清单就是下表，与第一节「状态」列由同一脚本（`scripts/ci/check_acceptance_matrix.py`）解析，实际检查：

- [产品合同](../产品合同.md)每个 `##` / `###` 章节必须在表里出现且只出现一次；
- 「对应断言」格给出至少一个真实存在的断言编号（多个用 `、` 分隔，连续区间可写成 `V-域-01…18` 形式），或写 `无对应断言`；留空即失败；
- 写 `无对应断言` 必须在「说明」里写明理由（不能只写 `—`）。

测试用例绑定尚未实装，需要测试与断言编号间的机器可读绑定，当前只有自由文本约定，留作后续。清单按章节粒度维护，不逐条抄合同规则，避免形成第二份合同正文；`V-部署-*` 等不对应合同章节的断言不要求出现在此。

| 合同章节 | 对应断言 | 说明 |
|---|---|---|
| 产品是什么 | 无对应断言 | 产品定位陈述，不含独立的可判定规则 |
| 用户与入口 | V-示例-01 | — |
| 不提供 | 无对应断言 | 这里换成你的：每条“不提供”都应由主动违规的否定断言承担，登记后替换本行 |
| 动态工作的去向 | 无对应断言 | 规定工作项去向（Issue / Project / PR），不产生用户可见规则 |

**这张表回答“哪条合同规则由哪些断言承担”，不回答“到哪一步了”**——后者看断言自己的状态列。两者分开维护：同一条断言可能被多个章节引用，把进度抄进这张表会立刻出现两个互相矛盾的副本。

**为什么不用覆盖率数字做门禁**：行覆盖率鼓励为达标而写的测试，且对“系统是否会拒绝违规行为”完全不敏感——一个 90% 覆盖率的套件可以一条否定测试都没有。合同条款覆盖清单是可数、可核对、且直接对应产品承诺的指标。
