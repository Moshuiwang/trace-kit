# 监控告警

> 出处：lingxi [#373](https://github.com/Moshuiwang/lingxi/issues/373)（D5 裁定：不引监控栈，宿主健康检查脚本 → 受控群告警，「服务持续 unhealthy 时有人知道」这一条闭环即可）、[#494](https://github.com/Moshuiwang/lingxi/issues/494)（stage 注入实证）；验证：stage 两次真实注入（脚本装于宿主、人为让容器转 unhealthy、群里如期收到告警与恢复通知）。

## 一、这一层解决什么问题

**应用内告警发现不了「发告警的那个进程自己已经死了」。** 两层告警的职责刻意不同：

| 层 | 谁在跑 | 能看见什么 | 看不见什么 |
| --- | --- | --- | --- |
| 应用内告警 | 挂在各服务**进程内部** | 依赖异常、任务滞留、发送失败等**业务级**故障 | **进程自己整个挂掉**——它没法在自己已经死掉之后还发出一条「我死了」 |
| 本文的宿主脚本 | 宿主 timer / cron，**在容器之外** | 容器整体不健康 / 不存在 / 未运行 / 重启循环——即「连报警的人都不在了」 | 任何业务级细节（哪个任务失败、哪个用户受影响），那些交给上面那层 |

两层不是互相替代，是互补：应用内覆盖「活着但出了业务问题」，宿主脚本覆盖「人（进程）已经不在了」。健康检查本身的两段判定语义（依赖可达 + 主循环活性）见 [`README.md`「健康检查」](README.md#健康检查不开放端口docker-exec-语义)——本文不重复，只**读取它的判定结果**（`docker inspect` 的 `State`）。

## 二、组件清单

| 文件 | 作用 |

## 三、安装

### 1. 把脚本放到宿主

脚本**不进任何镜像**，用 `git`/`scp` 复制到宿主即可（路径要与 systemd 单元里的 `ExecStart`、`WorkingDirectory` 一致；这里换成你的安装根目录）：

```bash
install -d -m 700 /opt/app/scripts /opt/app/monitoring
install -m 755 scripts/ops/host_health_alert.py /opt/app/scripts/host_health_alert.py
```

### 2. 建凭据文件（0600，与部署 env 文件同一条纪律）

凭据**不进 argv、不进日志**：脚本只接受一个文件路径参数（`--env-file`）。用 `install` 一步到位，别先 `cp` 再 `chmod`（那中间有一个短暂的可读窗口）：

```bash
umask 077
install -m 600 -o "$(id -un)" -g "$(id -gn)" /dev/null /opt/app/monitoring/host-monitor.env
# 然后往里写内容
```

文件内容（**只示例变量名，不示例取值**）：

```dotenv
ALERT_WEBHOOK_URL=
```

值可以用单引号或双引号包裹（脚本剥一层），**不支持变量展开、不支持转义**。权限不是 `0600`、属主不是当前用户、文件缺字段，脚本都会拒绝执行并以退出码 `2` 收尾（不静默降级）。

**这份凭据与容器内 `.env.<环境>.<服务>` 里的同名值是刻意重复的两份**：宿主脚本必须能在容器完全起不来时依然发出告警，因此不能依赖读取容器内的任何东西（`env_file:` 只注入容器，宿主进程读不到）。

### 3. 装周期触发

**有 systemd 时**（本目录已给出两个单元；`User=` 改成运行监控的宿主账户，它要能执行 `docker container inspect`，且必须是凭据文件的属主）：

```bash
install -m 644 deploy/monitoring-units/app-host-monitor.service /etc/systemd/system/
install -m 644 deploy/monitoring-units/app-host-monitor.timer   /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now app-host-monitor.timer
systemctl list-timers app-host-monitor.timer    # 核对 NEXT/LAST 时间戳在前进
```

**有 cron 时**（语义等效，二选一即可）：

```cron
* * * * * /usr/bin/python3 /opt/app/scripts/host_health_alert.py --env-file /opt/app/monitoring/host-monitor.env >> /opt/app/monitoring/cron.out 2>&1
```

- 每分钟一轮：脚本支持 1–2 分钟内任意频率，取 1 分钟能让第五节「时延估算」里轮询这一段最短。
- `--env-file` 是唯一必填参数，其余都有默认值：`--containers` 默认 `app-app-1`（一次性作业没有 `healthcheck`，天然不在覆盖范围），`--state-file`/`--log-file`/`--lock-file` 默认落在 `/opt/app/monitoring/` 下，另有 `--docker-bin`、`--timeout-seconds`。完整参数见 `--help`。
- `>> cron.out 2>&1` 只是兜底：脚本自己把结构化日志写进 `--log-file`，`cron.out` 只用来接住 logger 建好之前的失败（例如参数解析错误）。
- **装完先跑一次 `--dry-run`**（只判定、打日志，不真实发送、不落盘）：

  ```bash
  python3 /opt/app/scripts/host_health_alert.py --env-file /opt/app/monitoring/host-monitor.env --dry-run
  cat /opt/app/monitoring/host-monitor.log
  ```

### 4. 退出码

| 退出码 | 含义 |
| --- | --- |
| `0` | 本轮检查已完成——**不代表所有容器都健康**，健康结果体现在告警消息与状态文件里，不体现在退出码里；拿不到单实例锁（上一轮还没跑完）也算 `0`，不是故障 |
| `2` | 脚本自身故障，本轮未能完成检查：凭据文件缺失 / 权限不对 / 字段不全、`docker` 不可用或 daemon 问不到、状态文件写不了。值得让 timer 的日志与退出码体现出来，需要人工介入 |

## 四、告警语义

### 触发条件（`docker inspect` 判定）

直接信 docker 的判定，**脚本不自己攒连续失败计数**：

1. 容器不存在（`missing`）；
2. `State.Restarting == true`（`restarting`，重启循环）；
3. `State.Running == false`（`stopped`，例如 `exited`/`created`）；
4. `State.Health.Status == "unhealthy"`——**这一条本身已经隐含「持续」**：docker 的 `healthcheck.retries` 要求连续失败若干次才会把状态翻成 `unhealthy`。

`State.Health.Status == "starting"`（仍在 `start_period` 宽限期内）与**没有配置 `HEALTHCHECK`** 的容器都**不**触发——前者是正常启动期，后者是「这个容器本来就没有可比较的健康信号」。

**「问不到 daemon」不等于「容器不存在」**：`docker inspect` 非零退出时，只有 stderr 明确说「没有这个对象」才判 `missing`，其余一律当脚本故障（退出码 `2`）。把 daemon 抖动当成容器消失，会在 daemon 恢复时误报一条假恢复。

### 防骚扰（去重）

同一个容器、同一个原因只在**首次进入**时告警一次；原因不变，后续每一轮都不再发送。原因变化（例如从 `unhealthy` 变成 `missing`——容器在两次探测之间被整个删掉了）算新事件，允许再发一次：两种原因指向的排查动作不同。

去重靠 `--state-file` 指向的本地 JSON 记忆「上一次**已确认送达**的告警原因」，**只有发送成功之后才落盘**——发送失败不落盘，保证下一轮重新尝试同一个事件，而不是「发送失败也当作已经告警过，从此再也不重试」。状态文件写临时文件再 `os.replace` 原子替换，崩溃不会留下半截 JSON；文件损坏或格式不对按「从空状态开始」处理，不崩溃。

### 恢复通知

判定回到 `healthy`（或「本来就没配 healthcheck」）时发**一条**恢复通知，随后清空该容器的记忆。**处于告警态的容器观察到 `starting` 时，既不算新触发，也不确认恢复**——过早发一条恢复通知，很可能几十秒后宽限期结束又收到一条新告警，制造「刚说恢复又说挂了」的噪声；这种情况记忆原样保留，等下一轮拿到确定结果。

### 发送失败与单实例

发送失败（网络错误、超时、对端返回错误）只写本地日志，**不抛出未捕获异常、不让一轮因为一次网络抖动而崩掉**；失败的事件按上面「防骚扰」所述留到下一轮重试。同一时刻只允许一个实例真正执行检查（`fcntl.flock` 独占锁，`--lock-file`）——防止两个并发实例同时读旧状态、同时判定「需要告警」，绕开去重各发一条。**拿不到锁不是故障**，只是「上一轮还没跑完」，本轮安静让路。

**发送出口只有 `send_alert()` 一处**，默认按最通用的 incoming webhook 形状 POST `{"text": ...}`。**这里换成你的群 webhook 格式**（请求体、鉴权头、成功判定）；改这一个函数就够，判定与去重逻辑不需要动。

## 五、时延估算：从故障发生到告警送达（单一事实源）

> **本节是健康检查时延推导的唯一正文**，[`生产部署runbook.md`「七、观察期」](生产部署runbook.md#七观察期)引用本节结论、不维护第二份数字。改健康检查参数或活性阈值时，只更新这里。

**两种失败形状的最坏情形不一样，分开算：**

- **A 类：依赖不可达 / 进程崩溃**（健康检查命令自己立即失败或直接超时，不需要等待任何内部宽限）：
  `retries × (interval + timeout)`
- **B 类：主循环静默挂起**（进程还活着、依赖也连得上，但主循环因为一次未捕获异常或死锁停止消费）——这正是两段式健康检查要抓的那类「假健康」。要先等活性文件年龄超过阈值，检查才会开始报错，再叠加 docker 的重试节奏：
  `活性阈值 + retries × (interval + timeout)`

**公式里为什么要加 `timeout`**：docker 的健康检查周期是「跑一次检查（最坏耗时到 `timeout` 才判失败）→ 等 `interval` → 再跑下一次」，不是「每隔 `interval` 固定触发一次、检查耗时另算」。只用 `retries × interval` 会低估最坏情形。

**`start_period` 为什么不进这两个公式**：它只管「容器刚启动、还没等到第一次成功探测」那段窗口内的失败要不要计入 `retries`，是**启动阶段**的概念；本节两个公式建模的是「已经 `healthy` 的服务又出故障，多久会被重新判定为 `unhealthy`」。两个不同的时间窗口，不要互相替代。

**扩展点：健康检查如果对依赖探测结果做了短期缓存**（用缓存跳过建连开销），A 类公式要多两段：`(缓存 TTL + interval) + retries × (interval + timeout)`。多出来的 `+ interval` 是**网格量化**的安全上界——缓存过期只会在健康检查下一次被调用的那个离散节拍上被「发现」，不是过期那一刻就立刻触发真实探测。这一项漏掉过一次，让 A 类的真实最坏时延反超了 B 类，直接打破「A 类不超过 B 类」这条结论依赖的不变量（出处：[#409](https://github.com/Moshuiwang/lingxi/issues/409)）。取值约束：`TTL ≤ 活性阈值 − 2 × interval`（下限 0 即禁用缓存），比「不超过 B 类」的必要条件更保守，留出整整一个 `interval` 的显式余量。

**这里填你的现值与结果**（`interval`/`timeout`/`retries` 取自 `compose.yaml`，活性阈值取自健康检查实现）：

| 服务 | `interval` | `timeout` | `retries` | 活性阈值 | A 类 | B 类 |
| --- | --- | --- | --- | --- | --- | --- |
| `app` | 30s | 10s | 3 | 这里填你的 | 3×(30+10) = **120s** | 活性阈值 + 120s |

**docker 侧判定完成之后，还要加上宿主监控自己的两段延迟：**

- **轮询**：最坏情况是状态刚翻成 `unhealthy` 后脚本刚好错过这一轮，要等下一次调用——按每分钟一轮最多再加 **60s**（改成每 2 分钟就是 120s）。
- **出站 HTTP 往返**：按 **≤5s** 计；不含对端限流或故障导致的重试等待（那属于对端行为，也正是「发送失败留给下一轮重试」而不是本地无限重试的原因）。

**端到端最坏 = B 类 + 一个触发周期 + 出站往返**。这条闭环在本方案下是**几分钟量级**——实时监控栈能把它压到秒级，但那是另一条路线的取舍，「够用即可」的裁定下这个量级是刻意接受的成本。

### 转 healthy 判据（与上面两个公式是不同的窗口，不要互相替代）

上面回答的是「已经 `healthy` 的服务出故障后多久被判 `unhealthy`」；下面回答「服务刚启动，多久应该转 `healthy`」。

容器启动后，第一次探测在 `start_period` 内即可发生并可能成功，**一旦成功容器立即转 `healthy`，不需要等 `start_period` 结束**；`start_period` 只是「在它结束前，失败的探测不计入 `retries`」，不是「必须等它结束才能变 healthy」的下限。

**判据**：服务应在自身 `start_period` 加一个探测周期（`interval + timeout`）内出现至少一次成功探测并转为 `healthy`；超过这个窗口仍未转 `healthy`，才需要介入排查。**这里的数字不能拿上面 A/B 公式的结果来代替**——这两个窗口混用过一次，结果是拿一个偏大的期限去等一个本该很快出现的信号。

## 六、验证

- **本机**：把 `classify` / `decide_action` 两个纯函数的用例跑一遍——判定的七种状态、去重、原因变化、告警态下的 `starting`、恢复、凭据文件权限与格式校验、状态文件读写、`docker inspect` 的「命令缺失」「容器不存在」「daemon 不可达」三种边界。**每条断言都要做一次变异验红**，只跑绿的不算数。
- **真实注入（必须做一次，不能只做本机单测）**：在 stage 装好凭据文件与 timer 后，**人为让某个目标容器进入 `unhealthy`**（例如临时把该服务的依赖连接串改错，触发依赖不可达；主循环挂起这一类按实际条件选注入手法），观察：
  1. 群里是否在预期时延内收到一条告警；
  2. 恢复之后是否收到**一条**恢复通知，且此后不再重复；
  3. `--state-file` 事后回到清洁态。

  这一步是这一整层唯一的端到端证据。**装过一次、日志有输出，都不等于告警真的送得出去**——凭据错、webhook 地址错、对端拒收，前面每一层都不会红。

## 七、已知限制

- **监控自身失效是静默的**：timer/cron 被误删、宿主重启后没随之起来、锁文件因异常长期占用，都会让这一整层无声停摆——**没有另一层机制监视「这个监控本身还在不在跑」**。这是「够用即可」裁定下接受的边界，不是遗漏。缓解手段是**安装态核对**：定期确认 timer 条目存在、`LAST` 时间戳在持续前进、`--log-file` 有持续新增的时间戳（证明脚本确实在被周期性调用），而不是只信「当初装过一次」。
- 脚本假定宿主账户能直接执行 `docker container inspect`（在 `docker` 组或有等价权限）；账户权限本身的配置属于安装步骤，不在脚本职责内。
- 默认只监控常驻服务容器。一次性作业没有 `healthcheck`，天然不在覆盖范围——这是既有设计，不是缺口。
- 时延估算是基于 `compose.yaml` 与健康检查实现**现值**的理论推导，未经真实故障注入计时验证。**这两处任何一个数值改动，第五节的表要同步更新**——没有自动化门禁守着这个一致性，是人工核对纪律。
