# 验收前部署配置清单

> 出处：lingxi [#62](https://github.com/Moshuiwang/lingxi/issues/62) 的配套清单（b8ae10b，23 次修订）、[#203](https://github.com/Moshuiwang/lingxi/issues/203) 闸清单口径；验证：每批验收前跑一次，连续多个 Epic。

本清单只回答一个问题：**要让这条链路在一台机器上真的跑起来，需要配齐哪些东西，少配一样会死在哪里。**

它不是第二份部署文档——「怎么执行」在 [`README.md`](README.md)，「示例变量长什么样」在 [`.env.example`](.env.example)，「生产专属判据」在 [`生产部署runbook.md`](生产部署runbook.md)。本清单补的是它们之间缺的一层：**每一道「靠配置才能打开的闸」分别绑定哪些配置项、缺哪一项会导致哪一条职责不注册、用户会看到什么**。这一层不写下来就会散在几十条 Issue 评论与源码注释里，验收窗口现场现查要花掉半天。

> **闸在代码里全部开着，不代表任何一台机器上已经生效。** 能不能打开完全取决于这台机器的环境变量、卷挂载和随包配置文件是否配齐——这正是本清单要覆盖的内容。

## 一、闸清单：逐道要什么

**这里列你的闸。** 每道闸的「依赖」只列**这道闸独有**的配置项；进程启动本身必需的基础配置不在每道闸下重复——缺了它们进程根本起不来，属于「部署前置检查」层面的失败，不是本节要说的「进程正常运行、但某条职责悄悄不注册」这一类。

| 闸 | 需要的配置 | 缺失时的表现 | 自检方法 |
| --- | --- | --- | --- |
| 这里换成你的闸名 | 这里换成你的变量名 / 配置文件 / 卷 | 用户侧看到什么、日志里留下什么（错误码或审计事件名） | 第四节里的哪一层、跑哪条命令 |

写「缺失时的表现」时把这三种情况分开——它们排查方向完全不同，只看「有没有报错」看起来却一模一样：

1. **配置缺失**：职责整体不注册，留下一条明确的结构化审计（例如 `<职责>.duty_not_registered`，带 `reason`／`variable` 字段，只报变量名不回显值）。这一类第四节第二层就能查出来。
2. **配置存在但内容为空**：职责**照常注册**、健康检查照常绿、审计里什么也没有，只是每一轮判据恒为假，一件事都不会发生——只能靠「某张表一直没有新行」这个负面事实间接判断。这一类最容易被误读成「一切正常，只是还没人触发」。
3. **配置非法**（不是缺，是写错）：多数情况下应该让**整个进程拒绝启动**，波及全部职责，而不是只让这道闸静默失效。错配不是未配，两者的正确处置不同。

## 二、按进程分组：必需与可选

完整变量清单与逐条形状说明见 [`.env.example`](.env.example)（按服务分文件，不入库）；这里只标出**哪些是必需、哪些是可选、可选的缺了对应哪道闸**。

| 进程 | 必需 | 可选（缺了的后果见上一节对应闸） |
| --- | --- | --- |
| `app`（常驻） | 这里换成你的：业务库连接串等，缺了进程起不来 | 这里换成你的：闸门开关项，缺了只让某条职责不注册；调参项，缺了只影响吞吐 |
| `migrate`（一次性作业） | 迁移连接串（DDL 角色，与业务连接串**是两个变量**，迁移不回落到后者） | 无 |

写这张表时容易出的三类错，都在真实验收里被坐实过：

- **把「通知类配置」和「功能前置」并列成同一档可选**。两者捆在一起，会让「日报发到哪个群」这种纯通知配置决定「用户能不能被开通」——照那份表部署会得到「闸看起来全开、实际谁也开不了」。装配层要把它们解耦，清单也要分开写。
- **把「发布面」写成「独立可选」**。某个变量只决定某个执行面装不装配，但整条链路的最后一步正是靠这个面把结果写出去——缺它时意图只会堆在队列里，没有任何职责会消费。这类要标成**硬前置**。
- **把「有默认值」当成「可以不配」**。默认值安全不等于可以不知道它存在：「看不到这个变量」和「知道有这个变量、明确选择用默认值」是两件事。

**另有一类变量写在每服务 env 文件里不报错、也不生效**：compose 的取值优先级是 **`environment:` 块高于 `env_file:`**。凡是在 compose 的 `environment:` 块里显式声明过的变量，往 `.env.<环境>.<服务>` 里再写一遍会被原样覆盖掉，是一个不出声的错配。核对方法是**渲染后回读**而不是看 env 文件（出处：[#496](https://github.com/Moshuiwang/lingxi/issues/496)）：

```bash
docker compose --env-file deploy/.env.stage \
  -f deploy/compose.yaml -f deploy/compose.stage.yaml config app
```

## 三、前置资源（带外交付项）

**只写变量名与来源形态，不写任何真实值、坐标或主机名。**

### 持久卷

| 卷（stage / 生产） | 挂载点 | 与闸的关系 |
| --- | --- | --- |
| `app-{stage,prod}-data` | `/var/lib/app/data` | 这里换成你的：哪道闸真正依赖它、里面必须已经有什么 |

完整说明（备份周期、恢复策略、为什么按删除语义拆成不同的卷）见 [`README.md`「持久卷」](README.md#持久卷)。

### 数据库结构版本

数据库结构由 `migrate` 作业建立。**验收前核对当前库版本与镜像内置的迁移集合一致**：早于目标版本的库结构会让相关职责在真库操作阶段直接报「表不存在」，而不是本清单描述的「职责不注册」那一类静默失败。不一致时先跑 `migrate`，再启动常驻服务。

### 随镜像发布的配置文件

不经外置路径时，「配置是否齐备」取决于**镜像里带的是哪个版本**，而不是查某个环境变量。验收时应确认实际生效版本（候选镜像内置的那份，或外置路径指向的那份）与产品负责人最新拍板的版本一致——**不能假设「代码里有这份文件就等于内容是对的」**。

### 主密钥一类的带外交付项

以下变量的值**只能带外交付**（一次性生成后经受控渠道交给部署方，不进版本控制、不进 Issue/PR 正文），此处只登记名字与来源形态：

| 变量 | 来源形态 |
| --- | --- |
| 这里换成你的加密主密钥 | 一次性生成的密钥，长度与编码写清楚 |
| 镜像仓库只读拉取身份 | 部署机专用的**只读**令牌；**不得使用任何个人凭据**，也不得复用 CI 的令牌 |
| （数据，不是环境变量）首次授权产生的凭据 | 由某个一次性作业成功跑过一次产生，落在持久卷里；核对方式是**只核存在性与非空，不回显内容** |

### 本仓库之外的配置

**这一节是长期正文，不是一次性上线检查单。** 凡是配在外部平台后台、外部文档的协作者面板、或另一台机器上的东西，本仓库的 compose、`.env.*` 与门禁**都读不到**——因此这些项**没有任何一条会因为漏配而让 CI 变红**，漏了只会在运行时表现为「某条职责静默不工作」。**换环境（迁移、重建应用、换租户、测试转生产）必须逐项重做并重新核对一遍**，这正是把它们写进长期正文的原因。

这里列你的：每一项写清「配在哪」与「只读核对方式」（能用只读 API 探针就写命令，只能目视就写明由谁目视）。应用 ID 一类的非凭据标识可以写，密钥、令牌、文档坐标一律不进本表。

**这一节与本清单其余部分的关系**：第二节与第四节覆盖的是**这台机器上的配置**，全都能用命令核对；本节是**外部那一侧的状态**。两者都齐，闸才真的开着；只核其中一侧就宣布「配置齐了」，正是本清单开头点名要避免的那类结论。

## 四、自检方法：配完之后怎么确认真的生效

**「日志没报错」不构成证据。** 下面按「能看什么、能证明什么、**不能**证明什么」分五层，不接受「没报错就算过」这一类结论。

### 第一层：进程起没起来

**能证明**：必需配置齐了。**不能证明**：任何一道闸开着。

```bash
docker compose --env-file deploy/.env.stage -f deploy/compose.yaml -f deploy/compose.stage.yaml ps
docker compose --env-file deploy/.env.stage -f deploy/compose.yaml -f deploy/compose.stage.yaml logs app --tail 50
```

`healthcheck` 通过只证明两件事：依赖可达、主循环活性文件仍在更新（见 [`README.md`「健康检查」](README.md#健康检查不开放端口docker-exec-语义)）。**闸开没开，健康检查一律不知道**——一个闸全灭的进程照样能常年 `healthy`。

### 第二层：启动期职责缺失审计

**能证明**：哪些职责在启动期就被挡住了、缺了什么。**不能证明**：注册成功的职责真的在做事。

装配层发现前置不齐时应留一条结构化审计（只报变量名，不回显值）。启动后立刻查一次，**期望结果是零命中**：

```bash
docker compose ... logs app | grep -E '<你的职责名>\.duty_not_registered'
```

命中任何一条，按审计里的 `reason`／`variable` 对照第一节定位是哪一道闸。**这一层只覆盖启动期就能判定的前置缺失**，覆盖不到第一节列的第 2 类（配置合法但内容为空）与「代码接好了但这台机器没做过初次授权」这一类——它们都不产生这条审计，职责照常注册，在运行期逐个请求失败。

### 第三层：真实业务事实

**唯一能证明**「闸真的在发挥作用，不只是没被拦住」的层级。

这里换成你的：每道闸写一条**可查的真实事实**——某张表出现了新行且状态从 `pending` 推进到终态、某个文件确实为某个真实对象存在、某次真实外部调用返回的形状被正确解析。**没有真实旅程跑过一次，这一层拿不到任何证据**：闸开只保证「配置层面不会挡住」，不保证「真的有一条旅程走通过」。

注意「表是空的」本身不能区分「闸关着」和「还没有人触发」——所以这一层要主动触发一次，而不是等着看。

### 第四层：常驻作业的崩溃循环

崩溃循环往往比业务失败更容易被忽略：`restart: unless-stopped` 会让它持续产生「容器在运行」的假象（`ps` 显示 `Restarting`，或短暂 `Up` 之后又消失）。

```bash
docker compose ... logs app --tail 50 | grep -E '<你的启动期配置错误事件名>'
docker inspect --format='{{.RestartCount}}' <容器名>
```

**只看 `ps` 的 `STATUS` 列容易漏掉「起来几秒又崩了」**，一定要看重启次数或直接看日志里这类消息是否反复出现。

### 第五层：静态契约检查

**能证明**：配置文件 / 编排文件形状对。**不能证明**：运行时真的生效。

```bash
python3 scripts/ci/check_deploy_contract.py    # 文本级，不需要 docker
scripts/ci/verify_compose_structure.sh         # 渲染级，需要 docker compose v2
```

这一层只跑在 compose 与 `.env.example` 的源文件文本、以及渲染结果上，**不连接任何真实依赖**——它能拦住「编排文件写错了」，拦不住「环境变量在真机上确实没配」。两者要分开验证。

## 五、已知会踩的坑

以下每一条都能核实到出处，不是猜测。

1. **需要写入的持久卷挂成了 `:ro`**：第一次**写入**时才失败，表现与「完全没挂载」相同（职责不注册，其余职责与健康检查照常正常）。[`check_deploy_contract.py`](../scripts/ci/check_deploy_contract.py) 精确解析 `volumes:` 列表把这条变成会变红的检查——早期版本这里用子串包含判断，有过一个假绿口子（[#62](https://github.com/Moshuiwang/lingxi/issues/62)）。
2. **挂载路径的父目录不存在**：说明卷根本没挂对，**不是**「进程第一次运行时会自动建好」。只读该目录的进程不会自己 `mkdir`，它只会在装配期判定「前置不齐」然后不注册（[#62](https://github.com/Moshuiwang/lingxi/issues/62)）。
3. **两个服务共用同一个 `env_file`**：要么某个进程意外拿到它不该有的凭据（并继承给它拉起的每一个子进程），要么另一个进程拿不到必需变量而无限崩溃重启。`check_deploy_contract.py` 的 env_file 去重检查已经挡住这件事，没有例外（[#62](https://github.com/Moshuiwang/lingxi/issues/62)）。
4. **私有镜像仓库不登录**：`docker compose up` 停在 `failed to authorize ... 403 Forbidden`。必须先用只读拉取身份 `docker login`，见 [`README.md`「主机读取身份」](README.md#2-主机读取身份)（[#62](https://github.com/Moshuiwang/lingxi/issues/62)）。
5. **`--env-file` 忘记传**：`env_file:` 只把变量注入**容器**，不参与 compose 文件自身的 `${VAR:?}` 插值；省掉它 compose 会直接报变量未设并退出（[#62](https://github.com/Moshuiwang/lingxi/issues/62)）。
6. **`${VAR:-默认值}` 形态漏配不报错、静默退回默认**：资源限制就是这一类，加总可能因此超过主机内存。看 env 文件看不出漏没漏，必须靠 `config` 渲染回读（[#494](https://github.com/Moshuiwang/lingxi/issues/494)）。
7. **`environment:` 块的优先级高于 `env_file:`**：往每服务 env 文件里写一个已经在 compose `environment:` 块里声明过的变量，不会报错、也不会生效（[#496](https://github.com/Moshuiwang/lingxi/issues/496)）。
8. **`up -d` 在配置未变时不重启容器**：改的是挂载目录里的文件、宿主侧数据而不是 compose 配置时，compose 判 up-to-date 什么都不做。要重启用带全部 `--env-file`/`-f` 的 `restart`，裸跑 `docker compose restart` 会按 base compose 重建出缺 `env_file` 的容器（[#62](https://github.com/Moshuiwang/lingxi/issues/62)）。
9. **一次性作业配了重启策略**：会把「作业正常退出」变成无限重启循环，让人误以为服务已经上线；也会把一次失败的迁移变成反复撞墙并掩盖真正的失败原因。这条由门禁守着，改坏会变红（[#153](https://github.com/Moshuiwang/lingxi/issues/153)）。
10. **配置存在 ≠ 配置有效**：一个大到没意义的阈值等于把某条告警关掉，但配置本身看起来完全合法（范围校验挡不住「大到没意义」）。凡是阈值类配置，验收时要核对的是**值本身合不合理**，不是「有没有报错」。
