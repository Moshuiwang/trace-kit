# 生产部署 Runbook

> 出处：lingxi [#373](https://github.com/Moshuiwang/lingxi/issues/373)（S-H2-4 交付本文骨架）、[#521](https://github.com/Moshuiwang/lingxi/issues/521)（首次生产部署实录）；验证：stage 演练 + 生产首发一次（2026-09-02）。

> **定位声明**：本文写给到时执行生产部署的人照做，**它本身不构成执行授权**。任何一次真实生产执行（首次部署、升级、回滚、恢复演练）都必须先有一个独立的 `[ops]` Issue 完成开工前事实确认与授权；本文只提供步骤、判据和边界。
>
> **本文只写生产专属的判据与纪律**，逐字命令以 [`README.md`](README.md) 为准，不在这里复制第二份。两处冲突时以更晚更新的为准。
>
> **每次真实执行之后回来补一节「实录偏差」**：把当天与正文不一致的地方逐条写清「正文怎么写 / 实际怎么做 / 为什么」，下一次执行先读那一节。这一条是本 runbook 里最容易被跳过、也最值钱的一步——首发当天必然有正文没写到的东西，不记下来，下一个人要重新踩一遍。

## 二、首次部署步骤

### 2.1 准备 env 文件

按 [`README.md`「准备」](README.md#准备)为 `.env.prod`、`.env.prod.app`、`.env.prod.migrate` 写入生产值。

**生产凭据集与研发 / stage 凭据集完全隔离**：任何一个值都不得与 `.env.stage.*` 系列重复，也不得把研发环境的文件复制改名后当作生产文件使用。确有必须复用的例外（例如某个只有一份的外部端点凭据），必须是产品负责人对该值的显式授权，并且只注入真正需要它的那一个服务，不给其余进程继承。

**有默认值的变量必须靠渲染回读确认，看 env 文件看不出漏没漏**：`${VAR:?}` 形态漏配会让 `docker compose config`/`up` 直接失败，起不来；`${VAR:-默认值}` 形态漏配**不报错、静默退回默认值**。资源限制就是后一类——把 stage 的那一段原样复制进 `.env.prod` 会把生产静默降到 stage 量级，加总还可能超过主机内存。

```bash
docker compose --env-file deploy/.env.prod \
  -f deploy/compose.yaml -f deploy/compose.prod.yaml config app migrate
```

逐项核对渲染出来的资源数值与你写下的生产值一致，并核对所有常驻服务的 `memory` 加总小于主机内存、留出宿主与 Docker 守护进程的余量（推导见 [`README.md`「资源限制」](README.md#资源限制)）。

### 2.2 部署前置检查（preflight）

逐条通过 [`README.md`「部署前置检查」](README.md#部署前置检查preflight逐条通过才能-up)：三个 env 文件都 `0600` 且属主为部署用户；部署机已用**只读**拉取身份登录镜像仓库。任一项不符不得执行下一步。

这里加你的第三项：**本次发布意图涉及的开关变量，逐个确认实际取值是有意选的，不是漏配的结果**。做法是只读地打印那一行本身（不打印文件其余内容，且该变量不能是凭据），对照本次发布意图判断；取值不符或与意图不一致时先改配置再继续，不得带着未确认的取值起服务。

### 2.3 迁移

先跑一次性作业，再起常驻服务——顺序不能反：

```bash
docker compose --env-file deploy/.env.prod \
  -f deploy/compose.yaml -f deploy/compose.prod.yaml \
  --profile job run --rm migrate
```

作业**不配 restart**，失败会停下来让人看见；失败即停止本次部署，不要带着半截迁移起服务。

### 2.4 起常驻服务

```bash
docker compose --env-file deploy/.env.prod \
  -f deploy/compose.yaml -f deploy/compose.prod.yaml up -d
```

语义与 stage 完全一致，只替换了 `--env-file` 与覆盖文件——**这正是「stage 验过了所以生产也没问题」这句话成立的前提**，两份覆盖文件的结构等价由 [`../scripts/ci/verify_compose_structure.sh`](../scripts/ci/verify_compose_structure.sh) 每次 CI 比对。

### 2.5 健康回读

```bash
docker compose --env-file deploy/.env.prod -f deploy/compose.yaml -f deploy/compose.prod.yaml ps
docker compose --env-file deploy/.env.prod -f deploy/compose.yaml -f deploy/compose.prod.yaml logs app
```

判定标准见本文「七、观察期」，不在这里另立一套。

## 三、镜像 digest 固定

tag 是不可变约定，digest 是不可变**事实**：tag 由人维护，同一个 tag 被重新推送过、或本机缓存了同 tag 的旧镜像，都不会有任何东西报错。生产要固定到 digest。

`deploy/compose.yaml` 的镜像引用是 `${APP_IMAGE_REGISTRY:?}/app:${APP_IMAGE_TAG:?}${APP_IMAGE_DIGEST:-}`——`APP_IMAGE_DIGEST` 是**可选**后缀，默认空，不设时渲染结果与没有这一段逐字节一致。

**一个镜像一个 digest 变量，不要把 digest 塞进 tag 变量**：`APP_IMAGE_TAG` 是**多个服务共用**的（本骨架里 `app` 与 `migrate` 共用一份镜像，你的项目多半会有更多）。把 `<tag>@sha256:<digest>` 直接写进共用的 tag 变量，只能固定其中一个镜像；其余服务会解析成「这个 tag 对应的是另一份镜像的 digest」，拉取时报 `manifest unknown`。**镜像有几份，就加几个 digest 变量**：

| 变量 | 覆盖的 compose service |
| --- | --- |
| `APP_IMAGE_DIGEST` | `app`、`migrate`（同一份镜像） |
| 这里加你的 `<镜像>_IMAGE_DIGEST` | 用到该镜像的全部 service |

值的形状是 `@sha256:<digest>`（**注意前导 `@`**）：`tag@digest` 是合法的镜像引用，digest 优先生效、tag 仍供人读，因此不需要改 `APP_IMAGE_TAG` 本身，也不需要改 compose 结构。

**把 tag 解析成 digest（二选一，每份镜像各做一次）**：

```bash
# 方式一：直接查询远端仓库（推荐，不占本机磁盘）
docker buildx imagetools inspect <你的镜像仓库>/app:20260101-0123456789ab
# 输出里的 Digest: sha256:... 就是该 tag 当前指向的 manifest digest

# 方式二：已经 pull 到本机时，从本地元数据回读
docker pull <你的镜像仓库>/app:20260101-0123456789ab
docker inspect --format='{{index .RepoDigests 0}}' <你的镜像仓库>/app:20260101-0123456789ab
# 输出形如 <你的镜像仓库>/app@sha256:...，取 @ 之后的部分
```

写进 `deploy/.env.prod`（每份镜像一行；**前提是这些镜像确实来自同一次构建**——生产只拉不建，不会出现分别对应不同批次的情况）：

```dotenv
APP_IMAGE_DIGEST=@sha256:<本批次镜像 digest>
```

**部署后核对**：`up -d` 完成后执行

```bash
docker compose --env-file deploy/.env.prod -f deploy/compose.yaml -f deploy/compose.prod.yaml images
```

逐行核对每个服务实际运行的镜像 digest 与固定值一致。不一致说明本机存在同 tag 不同 digest 的缓存污染，必须先 `docker image prune` 或显式拉取该 digest 后重新 `up -d`；**不得在 digest 不匹配的状态下判定部署成功**。

## 四、单实例纪律

常驻服务在生产必须始终**单实例**。数据库级并发保护（行锁、CAS、唯一约束）挡得住数据写坏，挡不住「同一条外部通道被两个客户端同时握着」与「同一条通知发两遍」这类副作用；共享的外部通道往往是「新连接踢掉旧连接」语义，第二个客户端接上来会**静默**顶掉第一个。

**compose 里没有容器数量的硬约束**，因此这是运维纪律、不是被程序强制的边界：

- 任意时刻只允许一台机器、一个操作者持有对该环境的 compose 命令执行权，不得从两处并行 `up`/`scale`。
- 固定用普通 `up -d`（不加 `--scale`、不用 `--no-deps` 跳过依赖顺序）：compose 对已在运行的服务走「先让旧容器完全退出、再创建并启动新容器」的单容器替换流程，本身就满足单实例。
- 怀疑上一次部署没收口时，先 `ps` 核对没有残留旧容器（状态卡在 `Restarting`、或同一服务出现两个容器），确认干净再 `up -d`；不得在残留未清的状态下叠加新容器。
- 需要单独重启某个服务时，`stop <服务>` 等它完全退出再 `up -d <服务>`，**不用 `restart`**（部分场景下不保证严格的先停后起）。
- 这里换成你的：进程侧如果有代码级互斥（例如凭据目录里的文件锁），在这里写清哪些服务有、哪些没有——**没有的那些，纪律是它们唯一的保护**。

## 五、首发不灰度

灰度分流（按版本把流量切成两份）如果只有设计正文、没有可运行的载体，**首次发布就按整体切换执行**：一次 `up -d` 替换全部常驻服务，不启用也不能启用不存在的机制。灰度留待真实需求触发（需要按小流量放量验证新版本行为，而不是每次发布都全量切换），触发时单独立项实施与验收，不在本 runbook 预支。

## 六、回滚判据与步骤

**判据**：本文「七、观察期」判定为不健康，或部署后短时间内出现明确的业务异常（日志持续报错、外部通道建不起来、任务领不到）。

**回滚 = 回退镜像引用后 `up -d`，绝不重建**。如果仓库不锁传递依赖，同一个 commit 在不同日期重新构建不保证逐字节一致；**镜像制品本身才是可信的回滚单位**，回滚不能通过「回退代码 + 现场 `docker build`」实现——生产编排里一个 `build:` 键都没有，正是为了让这条路径不存在。

```bash
# 1. 把 deploy/.env.prod 的 APP_IMAGE_TAG 改回上一个候选批次，并把每个
#    <镜像>_IMAGE_DIGEST 改回该批次各自的 digest（见「三、镜像 digest 固定」的变量
#    对照表——一个镜像一个变量，不是把 digest 塞进 APP_IMAGE_TAG）

# 2. up -d：compose 按「四、单实例纪律」的替换流程逐个服务先停旧再起新
docker compose --env-file deploy/.env.prod \
  -f deploy/compose.yaml -f deploy/compose.prod.yaml up -d

# 3. 回读确认实际运行 digest 与目标一致（见「三、镜像 digest 固定」）
docker compose --env-file deploy/.env.prod \
  -f deploy/compose.yaml -f deploy/compose.prod.yaml images
```

**回滚不触碰数据库与持久卷**：不执行 `down -v`，不做任何迁移降级。这一前提成立的条件是**迁移遵守「先加后删」**——破坏性变更必须拆成两次发布，否则回滚就从「切镜像重启」变成「恢复数据库备份」。把这条钉成机械核对的门禁断言，不要靠记性。

## 七、观察期

> 时延数值的单一事实源是 [`监控告警.md`「时延估算」](监控告警.md#五时延估算从故障发生到告警送达单一事实源)。本文只引用「最坏时延」这个结论，不维护第二份数字——改健康检查参数时只需更新那一份表。

**部署后至少持续观察 15 分钟**（覆盖最坏端到端发现时延的两倍以上，留出多个健康检查周期的余量），期间：

- 每隔 1–2 分钟 `ps` 一次，确认常驻服务状态列为 `healthy`、重启计数不再增长（部署本身触发的一次容器创建不算异常重启）；
- 抽查最近若干次健康检查记录，确认没有非预期的失败探测：

  ```bash
  docker inspect --format='{{json .State.Health.Log}}' <容器名>
  ```

- 核对应用层信号：日志无持续报错、该建立的连接已建立、主循环已进入正常节奏（不要求已经真实处理业务任务）。

**两条判据分属不同窗口，不要互相替代**：

1. **转 healthy**：各服务应在自身 `start_period` 加一个探测周期（`interval + timeout`）内转为 `healthy`。**这条用的是 `start_period`，不是「服务持续不健康要多久才被发现」的那组数字**——那是另一个窗口（推导见 [`监控告警.md`「转 healthy 判据」](监控告警.md#转-healthy-判据与上面两个公式是不同的窗口不要互相替代)）。这两个窗口混用过一次，会让人拿一个偏大的期限去等一个本该很快出现的信号，把真正的启动故障当成「还没到时候」。
2. **观察窗口内保持 healthy**：15 分钟结束时全部常驻服务 `healthy` 且无非预期重启，判定本次部署成功，转入正常运行。观察期内出现非预期重启，或任一服务转回非 `healthy`，判定部署失败，进入「六、回滚判据与步骤」。

## 八、恢复演练要求

**生产首次部署前应至少完成一次真实的数据库恢复演练**，核对下面这条补偿动作确实被执行且结果符合预期。本文只登记要求，不代为执行。

数据库从备份恢复后、重新对外提供服务之前，**必须先按内容原始写入时间重新执行一轮保留期清理**：备份或 WAL 中无法逐条即时删除的内容（含尚未结束的保留窗口）按**原写入时间**计算到期，不能把恢复完成的时间当成新的保留起点，也不能借这次恢复重新打开一个已经结束的窗口。恢复历史备份会重新带回备份时已有的用户内容——这是已经接受的灾备取舍，但「重新提供服务前先补清理」是这条取舍成立的前提，不是可选步骤。这里换成你的：有内容保留期承诺时按上面这条做；没有时，写清你这边恢复后必须补做的是什么。

演练未做而首发在即时，豁免必须是产品负责人的显式决定、写清适用范围与撤销条件，且**只对本次有效**，不构成后续升级的常设豁免。

## 九、secret 注入与凭据隔离

- **完全隔离**：生产凭据集与研发 / stage 凭据集不共用任何值。例外必须由产品负责人显式授权，且只注入真正需要它的那一个执行路径，不给无关进程继承。
- **stage 不动**：本节只约束生产，不改动 stage 既有的注入方式。
- **首发起步形态**：Docker secrets 或 `0600` env 文件二选一都满足要求。[`README.md`](README.md) 按 `0600` env 文件给命令；选 secrets 时按 Compose 的顶层 `secrets:` 与逐服务挂载改写，「凭据不进 `--env-file` 明文」的效果与 `0600` 文件等价。
- **迁移到操作系统级密钥管理是后续路线，书面登记、不在首发落地**。触发条件（满足任一即评估启动）：监管或审计提出强制要求；需要频繁轮换而手工替换 `0600` 文件不可持续；需要向多主机分发同一份生产凭据。形态候选：宿主原生的凭据机制（不引入新的常驻服务）、或云厂商托管密钥服务；具体选型在触发时由独立工作项决定，本文不预先选定供应商。

## 十、监控与日志

生产部署之后的持续可观测性不在本文展开：

- **基础设施层监控与告警**：[`监控告警.md`](监控告警.md)。「七、观察期」结束之后的长期故障发现路径以它为准，本文不重复维护阈值。
- **容器日志留存**：容器 stdout 日志由 Docker 的日志驱动轮转（`max-size`/`max-file`，见 `compose.yaml`），**容器被替换即丢失**——它是取证窗口的第一层缓冲，不是留存方案。需要跨重部署留存时，这里加你的：宿主侧增量收集 + 轮转（一个把容器日志按增量抄到宿主持久目录、再交给宿主轮转工具的定时作业）。升级前先把当前容器日志 flush 到宿主持久目录，见 [`README.md`「安装与升级」](README.md#安装与升级)。
